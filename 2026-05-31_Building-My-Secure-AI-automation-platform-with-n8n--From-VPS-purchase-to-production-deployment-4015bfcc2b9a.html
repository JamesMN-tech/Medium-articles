Building My Secure AI automation platform with n8n: From VPS purchase to production deployment

When I first decided to build my own AI automation platform, I knew I wanted complete control over the environment. Rather than relying on third-party cloud automation services, I wanted to host everything myself, learn the infrastructure, and create a foundation that could support future AI agents and automation workflows.

This is the story of how I went from purchasing a VPS to deploying a fully secured, SSL-enabled n8n automation platform.

The Goal

My objective was simple:

Build a production-ready automation server that could securely run AI agents, Gmail automations, API integrations, and future workflows without depending on external platforms.

The final destination would become:

https://n8n.jamesmn.tech

Step 1: Purchasing the Infrastructure

I started by purchasing a two-year VPS hosting plan from Hostinger along with my custom domain:

jamesmn.tech

The VPS provided a clean Ubuntu environment with full administrative control and Docker support, giving me everything I needed to build a self-hosted automation platform.

Step 2: Setting Up Ubuntu

After provisioning the VPS, the first task was getting the server updated and cleaned up.

A fresh server is rarely fully up to date, so I ran the usual maintenance commands to update packages, install security fixes, and remove unnecessary files. This ensured I was starting with a stable foundation before deploying anything important.

Step 3: Installing Docker

Since I planned to run multiple services together, Docker was the obvious choice.

Docker provided several advantages:

  • Easy deployment
  • Simplified upgrades
  • Service isolation
  • Better portability
  • Cleaner networking

Using containers meant I could deploy, manage, and troubleshoot services much more efficiently than running everything directly on the host operating system.

Step 4: Deploying n8n

With Docker ready, I deployed n8n using Docker Compose.

The deployment included:

  • n8n automation platform
  • Traefik reverse proxy
  • Docker networking
  • Automated SSL support

At this point, everything appeared to be running, but I quickly ran into my first major challenge.

Step 5: The SSL Headache

When I opened the site in Chrome, I was greeted with some intimidating messages:

  • “Not Secure”
  • “Dangerous Website”

Not exactly the welcome screen I was hoping for.

The issue was SSL. Browsers weren’t trusting the connection, which meant HTTPS wasn’t functioning correctly.

Solution was to use a different browser in this case microsoft edge .

Step 6: My Certbot Detour

Like many Linux administrators facing SSL issues, my first instinct was:

“Let’s install Certbot.”

I attempted to generate certificates manually using Certbot and Nginx.

Unfortunately, that quickly led to another problem.

Port 80 was already occupied.

Step 7: Discovering What Was Already There

After investigating running services and checking active ports, I discovered something important:

Traefik was already handling ports 80 and 443.

In other words, I was trying to solve a problem that had already been solved by the existing Docker stack.

Traefik had been configured to automatically manage SSL certificates through Let’s Encrypt. My task wasn’t to install Certbot — it was to fix the Traefik configuration.

That realization saved me from heading down the wrong path.

Step 8: DNS Troubleshooting

Next came DNS configuration.

I configured the required DNS records for my domain and subdomain so traffic could properly reach the VPS.

Everything looked correct, yet SSL still refused to generate.

After more investigation, I found the culprit.

The Hidden IPv6 Problem

An incorrect IPv6 (AAAA) record existed in DNS.

Let’s Encrypt validation was attempting to use that record and failing.

Once I removed the bad IPv6 entry, SSL certificate generation finally succeeded.

This was one of those troubleshooting moments that reminds you how a single overlooked DNS record can cause hours of confusion.

Step 9: Updating the Environment Configuration

The next fix involved updating the environment variables used by the Docker deployment.

The original configuration referenced a temporary Hostinger hostname.

I replaced it with:

  • Domain: jamesmn.tech
  • Subdomain: n8n
  • Timezone: America/New_York

After updating the configuration, I restarted the Docker stack to force Traefik to reload its settings and request fresh certificates.

Step 10: Success at Last

After restarting everything, I tested the endpoint.

This time the results were exactly what I wanted:

  • Valid Let’s Encrypt certificate
  • TLS 1.3 enabled
  • HTTP/2 active
  • Successful certificate verification

The SSL deployment was finally working.

Step 11: The Chrome Cache Trap

Just when I thought the battle was over, Chrome continued showing warnings.

The server was secure.

The certificate was valid.

Everything checked out.

The problem turned out to be Chrome itself.

The browser had cached old HSTS policies from earlier failed SSL attempts.

After clearing the cached HSTS entries, the warnings disappeared immediately.

Sometimes the hardest bugs aren’t on the server at all.

Step 12: Hardening the Server

With SSL working, I shifted my focus to security.

I removed an insecure Traefik dashboard setting that exposed internal administration features publicly.

Then I installed:

UFW Firewall

Allowing only essential ports:

  • SSH (22)
  • HTTP (80)
  • HTTPS (443)

Fail2Ban

To automatically detect and block brute-force login attempts.

Security isn’t something you add later. It’s something you build into the platform from the beginning.

The Final Architecture

The finished request flow looks like this:

Internet
    ↓
Hostinger DNS
    ↓
Traefik Reverse Proxy
    ↓
HTTPS / TLS Encryption
    ↓
n8n Docker Container

Simple, secure, and scalable.

What’s Next: AI Agents

The infrastructure wasn’t built just for automation.

The real goal is AI.

One of the first planned projects is a Kenya Daily News Briefing Agent that will:

  1. Collect news headlines from trusted sources
  2. Use AI to summarize the stories
  3. Generate a concise briefing
  4. Deliver it via Gmail every morning at 9 AM Eastern Time

This is exactly the type of workflow n8n excels at.

The possibilities are almost endless.

Lessons Learned

This project ended up teaching me far more than I originally expected.

Along the way I gained hands-on experience with:

  • Linux administration
  • Docker containers
  • Reverse proxies
  • SSL/TLS deployment
  • DNS troubleshooting
  • Cloud hosting
  • Infrastructure security
  • DevOps practices
  • AI automation platforms

Most importantly, I learned that troubleshooting is rarely about the first problem you see. It’s about following the evidence until you uncover the real cause.

Final Thoughts

What started as a simple VPS deployment evolved into a secure, production-ready automation platform capable of supporting AI agents, workflow automation, webhooks, Gmail integrations, and future development projects.

The platform is now live, secure, and ready for whatever comes next.

And honestly, the troubleshooting journey taught me just as much as the successful deployment itself.

The server is running. The certificates are valid. The foundation is built.

Now it’s time to start creating AI agents. 🚀
